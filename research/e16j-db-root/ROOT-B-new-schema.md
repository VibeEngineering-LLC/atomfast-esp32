# ROOT-B: идентификатор записи при измерении + новая схема базы (вариант Б)

Дата: 2026-11-14. Код: `<репозиторий прошивки>`, HEAD `a27d2aa`; версия заказчика `e16j-ota-auth` (`0bb9001`). Путь доставки в e16j и HEAD совпадает: `git diff e16j-ota-auth HEAD -- main/af_pg.c main/pg_batch.c main/pg_csv.c` показывает только маску включённых колец и новые модели датчиков. ESP-IDF 5.4.0 (`dependencies.lock:12-15`), LittleFS-компонент 1.23.1 (`dependencies.lock:25`). PostgreSQL ≥ 14 (DDL `:10`), документация цитируется по версии 17.

## Резюме

1. **Механизм.** Записи присваивается неизменный идентификатор `(life, seq)`:
   - `life` — случайный UUIDv4, создаётся один раз на «жизнь» раздела данных и хранится в нём;
   - `seq` — уже существующий номер записи в кольце.
2. Плата отправляет только записи, уже сброшенные на флеш. Поэтому номер, побывавший в базе, никогда не выдаётся повторно.
3. Курсор хранит база: в начале сессии `SELECT seq … WHERE life=$1 ORDER BY seq DESC LIMIT 1`. Курсор в NVS, перенос эпохи и `gen = epoch` удаляются.
4. Полное стирание даёт новый `life`. Совпасть со старыми строками он не может: вероятность 9·10⁻²⁶ на миллион жизней.
5. **Стандартный приём:** стабильный идентификатор у источника, идемпотентный приёмник (`ON CONFLICT (life, seq) DO NOTHING`), доставка at-least-once. Подтверждение — кумулятивное, со стороны приёмника.
6. **Самопроверка, сценарии а–з:** потерь по вине механизма 0, дублей 0, остановок, которые требуют решения человека для корректности, 0. Отдельно учтены:
   - неотправленное, которое уничтожает само стирание: это действие пользователя;
   - диалоги по букве ТЗ 2.2.1;
   - однократная установка схемы в пустую базу.
7. **Цена для прошивки:** около +330 / −90 строк кода, около 300 строк тестов.
8. **Цена для администратора базы:** один скрипт `af_migrate_life.sql` под владельцем таблиц, до обновления прошивки. Работает онлайн, кроме двух коротких блокировок ACCESS EXCLUSIVE на таблицу. Старые прошивки продолжают писать в мигрированную базу.

## 2. Выбор идентификатора

### (а) `life` (UUIDv4 жизни раздела данных) + `seq` — ВЫБРАН

- **Уникальность после любого числа стираний.** Каждая жизнь получает 122 случайных бита (RFC 9562 §5.4). По формуле дней рождения вероятность совпадения хоть одной пары:
  - n = 10³ жизней — 9,4·10⁻³²;
  - n = 10⁶ — 9,4·10⁻²⁶;
  - n = 10⁹ — 9,4·10⁻²⁰.
- Внутри жизни `seq` строго возрастает: повторной выдачи отправленного номера нет (§3.2). Запас счётчика: 2³² при 0,518 записи/с — 263 года.
- **Условие на генератор.** В ESP-IDF v5.4 (ESP32-S3, «Random Number Generation») `esp_random()` даёт истинно случайные числа, пока включён Wi-Fi или Bluetooth либо вызван `bootloader_random_enable()`. Иначе выход «should be considered as pseudo-random only». RFC 9562 §6.9 рекомендует CSPRNG. Правило: `life` генерируется лениво, при первом сбросе с данными или первой отправке, и только когда радио включено (§3.1).
- **Хранение на устройстве:**
  - файл `/storage/h/life.bin` ≈ 48 Б, раз на жизнь: `life` 16 Б, MAC владельца 6 Б, «пол» 3×4 Б, флаги, CRC;
  - 48-битный отпечаток `life` в резервных байтах 24..29 заголовка сегмента;
  - на запись — 0 Б в ОЗУ и на флеше.
- **Почему `life.bin` в разделе данных, а не в NVS.** Пространство номеров `seq` живёт в LittleFS: это `first_seq` сегментов. Поэтому идентичность пространства должна жить там же:
  - стёрли NVS — `seq` продолжается, `life` тот же;
  - отформатировали `storage` — `seq` начинается с 0 под новым `life`.

### (б) UUIDv7 / ULID на запись — отклонён

- Уникальность обеспечивают 74 случайных бита на запись (RFC 9562 §5.7). Неверные или откатившиеся часы её не ломают, ломают только упорядоченность: §6.1 и §6.2 упоминают «clock rollbacks», а §6.1 не даёт никаких гарантий точности часов.
- **Размер:** +16 Б на запись. Сырые 20 → 36 Б (+80 %, ёмкость ×0,556), агрегаты 28 → 44 Б (+57 %), среда 14 → 30 Б (+114 %). При тех же 3,77 МБ охват сырых падает с 4,21 до 2,34 сут.
- `seq` всё равно нужен для курсора и порядка в кольце, поэтому UUIDv7 ничего не убирает и только добавляет 16 Б на запись. Кроме того, это 16 Б генератора на каждую запись, а условие ESP-IDF на генератор действует и здесь.

### (в) Иные

- **`life` 64 бита вместо UUID.** n = 10⁶ — 2,7·10⁻⁸, n = 10⁹ — 2,7·10⁻². Выигрыш 8 Б на строку в базе. Отклонён: UUID — стандартный тип PostgreSQL (§8.12), а разница в цене ничтожна.
- **`gen` = 31-битная свёртка `life` в старом столбце, без смены схемы.** Вероятность совпадения на один `hwid`: L = 100 жизней — 2,3·10⁻⁶, L = 1000 — 2,3·10⁻⁴. Это граница варианта А, здесь не развиваю.
- **Номер жизни выдаёт база при «установить соединение».** Отклонён: записи до первого подключения остались бы без идентификатора, а при смене базы (сценарий е) номер другой базы не уникален.
- **Счётчик в eFuse.** Отклонён: биты необратимы и ограничены.

### Нужна ли «сверка с базой при подключении» и диалог 2.2.1

- **Для корректности не нужна.** Совпадение ключей разных жизней исключено конструкцией, перенумерация (ТЗ 2.2.4 «поднять эпоху») не требуется.
- **Букву ТЗ выполняем информационно.** «Установить соединение» = вход + проверка схемы (`SELECT life FROM af_raw LIMIT 0`; ошибка 42703 → «база не обновлена, выполните `af_migrate_life.sql`», флаг не ставится) + `SELECT EXISTS (SELECT 1 FROM af_raw WHERE life IS DISTINCT FROM $life)`, то же для `af_agg`/`af_env`.
  - Есть чужие строки → диалог дословно по ТЗ:18. «Да» → флаг = true, «отмена» → false (2.2.2).
  - Пусто или строки только своей жизни → флаг молча (2.2.5, 2.2.8).
- **Решение заказчика:** пункт 2.2.4 становится пустой операцией. Плата ничего не перенумеровывает, и `gen/epoch` больше не ключ.

## 3. Механизм на плате

### 3.1 Жизнь

1. **Загрузка и восстановление** (`af_pfs_restore`, `af_persist_fs.c:375`):
   - читается `life.bin` (CRC);
   - если файла нет, а у новейшего сегмента отпечаток нулевой, это **переход с e16j**. «Пол» = `acked+1` из старого курсора NVS (`s_cur[k]`, `af_pg.c:257-275`), если `valid`, иначе 0;
   - если отпечаток ненулевой, а `life.bin` нет — **аномалия R-A4**: «пол» = текущий `head`, счётчик `life_lost`++;
   - если нет ни файла, ни сегментов — новая жизнь, «пол» = 0.
2. **Генерация.** `life` создаётся (`esp_fill_random`, затем биты версии 4 и варианта) и записывается в `life.bin` (временный файл + rename) до первого сброса с данными. Условие — включён Wi-Fi или BT. Если радио ещё не включено, сброс откладывается.
3. **Отпечаток:** первые 6 байт `life` пишутся в байты 24..29 каждого нового заголовка сегмента. Версия формата остаётся `AF_SEG_VER 1`: e16j читает такой заголовок (байты не проверяются, `af_persist.h:66-88`) и не удаляет сегменты при откате.
4. **ОЗУ-режим** (LittleFS не смонтирован): `life` новый на каждую загрузку, в момент первой отправки; граница «только сброшенное» не действует. Данные не переживают перезагрузку, поэтому повтор номера под тем же `life` невозможен.
5. **Проверка свежей жизни:** если `sent_any = 0` (флаг в `life.bin`), а в базе уже есть строки с этим `life`, генератор совпал. `life` пересоздаётся: строк этой жизни ещё нет, терять нечего.
6. **MAC владельца:** записывается в `life.bin` при выборе прибора. В `ble_sel_cmd.h:17` при `!has_tgt` сравнение идёт с ним. Тот же дозиметр после стирания настроек → очистка не нужна.

### 3.2 Номер не выдаётся повторно

- Верхняя граница плана отправки = `min(head, persisted_seq[k])`; `persisted_seq` растёт только после `fclose` (`af_persist_fs.c:516`, `:558`).
- После обрыва питания восстановленный `end_seq` не меньше любого отправленного номера. Повторно выданные номера принадлежали только несброшенному хвосту, а он в базу не уходил.
- «Отправить сейчас» сначала вызывает `af_pfs_flush_now()` (`af_persist_fs.c:950`).

### 3.3 Курсор = база

- В начале сессии на каждое включённое кольцо выполняется `SELECT seq FROM af_raw|af_agg|af_env WHERE life=$L ORDER BY seq DESC LIMIT 1`. Индекс `(life, seq)` читается с конца и отдаёт первую строку без просмотра остального (PostgreSQL 17 §11.4). Разбор одной колонки DataRow уже есть (`af_pg_plan.h:290`).
- Начало = max(ответ+1 или 0, «пол»[k], старейший в кольце). Если ответ+1 меньше старейшего, записи вытеснены до отправки: это видимая дыра `seq` в базе, плюс счётчик.
- Если ответ ≥ `head` (база впереди платы), это **аномалия R-A3**: счётчик, журнал, предупреждение в UI. Отправка продолжается, конфликтные строки видны как `rows - ins`, `af_pg.c:981`.
- Курсор в NVS (`af_pg.c:244-275`, `:984-996`, `:1210-1216`), перенос эпохи (`:796-805`) и `gen = epoch` (`:838-844`) удаляются.

### 3.4 Запрос вставки

- Строка: `INSERT INTO af_raw (life,seq,ts,epoch,hwid,doserate,dose,c2s,cps,n,ring,kind,charge,t,flags) VALUES ('<32 hex>',…),… ON CONFLICT (life,seq) DO NOTHING;`
- `gen` не передаётся, станет NULL. `epoch` остаётся справочным.
- UUID без дефисов допустим на входе (PostgreSQL 17 §8.12). Литерал в `INSERT … VALUES` приводится к типу столбца.
- Плюс ≈ 35 Б на строку: пачка при том же буфере станет короче примерно на четверть. Измерением не проверено.

## 4. Схема базы и миграция

### 4.1 Целевое состояние (для каждой из `af_raw`, `af_agg`, `af_env`)

- Новый столбец `life uuid NULL`. У старых строк NULL, у строк новой прошивки — значение.
- `gen` — `NULL` допустим, DEFAULT снят. Старые прошивки и `af_ingest` передают `gen` явно (DDL `:304`, `pg_batch.c:275`).
- `CHECK ((life IS NULL) <> (gen IS NULL))` — у строки ровно одна схема идентичности.
- Уникальный индекс `(life, seq)` — арбитр новой прошивки. NULL в уникальном индексе по умолчанию различны (PostgreSQL 17, CREATE INDEX, «NULLS DISTINCT»), поэтому старые строки не мешают.
- Уникальный индекс `(hwid, ring, gen, seq)` — арбитр старых прошивок и `af_ingest`. Неполный индекс выводится для `ON CONFLICT (cols)` (PostgreSQL 17, INSERT: «a non-partial unique index … will be inferred»). Строки новой прошивки с `gen IS NULL` в нём не конфликтуют.
- Ограничение `af_*_pk` удаляется. PRIMARY KEY требует NOT NULL, а у старых строк `life` = NULL. Принятый риск R-A12.

```sql
-- 0. Остатки неудачных CONCURRENTLY (невалидные индексы): удалить до повтора
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;   -- если есть af_*_uq: DROP INDEX CONCURRENTLY
-- 1. Столбцы: без перезаписи таблицы
ALTER TABLE af_raw ADD COLUMN IF NOT EXISTS life uuid;
ALTER TABLE af_agg ADD COLUMN IF NOT EXISTS life uuid;
ALTER TABLE af_env ADD COLUMN IF NOT EXISTS life uuid;
-- 2. Индексы онлайн (по два прохода таблицы каждый)
CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS af_raw_life_seq_uq ON af_raw (life, seq);
CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS af_raw_legacy_uq   ON af_raw (hwid, ring, gen, seq);
CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS af_agg_life_seq_uq ON af_agg (life, seq);
CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS af_agg_legacy_uq   ON af_agg (hwid, ring, gen, seq);
CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS af_env_life_seq_uq ON af_env (life, seq);
CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS af_env_legacy_uq   ON af_env (hwid, ring, gen, seq);
-- 3. Короткая транзакция на таблицу (ACCESS EXCLUSIVE); повторный запуск безопасен
DO $$ BEGIN
  IF EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'af_raw_pk') THEN
    ALTER TABLE af_raw DROP CONSTRAINT af_raw_pk;
    ALTER TABLE af_raw ALTER COLUMN gen DROP NOT NULL, ALTER COLUMN gen DROP DEFAULT,
      ADD CONSTRAINT af_raw_id_one CHECK ((life IS NULL) <> (gen IS NULL)) NOT VALID;
  END IF;
END $$;
-- то же для af_agg (af_agg_pk, af_agg_id_one) и af_env (af_env_pk, af_env_id_one)
-- 4. Проверка старых строк без блокировки записи
ALTER TABLE af_raw VALIDATE CONSTRAINT af_raw_id_one;
ALTER TABLE af_agg VALIDATE CONSTRAINT af_agg_id_one;
ALTER TABLE af_env VALIDATE CONSTRAINT af_env_id_one;
-- 5. Представление подозрений на дубль: жизнь вместо поколения (тип и имена столбцов прежние)
CREATE OR REPLACE VIEW af_dup_suspects AS
SELECT 'raw'::text AS tbl, hwid, ts, count(*) AS copies, count(DISTINCT coalesce(life::text, 'g'||gen)) AS gens
  FROM af_raw GROUP BY hwid, ts, doserate, dose, c2s, charge, t HAVING count(DISTINCT coalesce(life::text, 'g'||gen)) > 1
UNION ALL
SELECT 'agg'::text, hwid, ts, count(*), count(DISTINCT coalesce(life::text, 'g'||gen))
  FROM af_agg GROUP BY hwid, ts, kind, doserate, dose, c2s, charge, t HAVING count(DISTINCT coalesce(life::text, 'g'||gen)) > 1;
```

### 4.3 Блокировки и время (по документации)

| Шаг | Блокировка | Мешает ли INSERT платы | Время |
|---|---|---|---|
| 1 ADD COLUMN без DEFAULT | ACCESS EXCLUSIVE (ALTER TABLE: «An ACCESS EXCLUSIVE lock is acquired unless explicitly noted») | на миг | без перезаписи: «In neither case is a rewrite of the table required» (ALTER TABLE, Notes) |
| 2 CREATE UNIQUE INDEX CONCURRENTLY | SHARE UPDATE EXCLUSIVE (§13.3.1). ROW EXCLUSIVE с ней не конфликтует | нет | два прохода таблицы, ожидание старых транзакций (CREATE INDEX, «Building Indexes Concurrently»); вне транзакционного блока |
| 3 DROP CONSTRAINT, DROP NOT NULL/DEFAULT, ADD CHECK NOT VALID | ACCESS EXCLUSIVE | на время транзакции | NOT VALID пропускает проверку существующих строк (ALTER TABLE, ADD table_constraint) |
| 4 VALIDATE CONSTRAINT | SHARE UPDATE EXCLUSIVE (ALTER TABLE, VALIDATE CONSTRAINT и Notes) | нет | один проход таблицы |

- `lock_timeout` (PostgreSQL 17 §19.11.1) прерывает ожидание блокировки. Шаги 1 и 3 при отказе просто повторить.
- Неудачный CONCURRENTLY оставляет «invalid» индекс: «drop the index and try again» (CREATE INDEX).
- Места на диске: плюс два индекса, минус индекс PK. Итог — примерно ещё один индекс размером с PK. Не измерено.

### 4.4 Права

- ALTER TABLE: «You must own the table to use ALTER TABLE» (ALTER TABLE, Description). Выполняет владелец объектов, тот же, что применял DDL (DDL `:5`).
- Прав роли платы менять не нужно. SELECT и INSERT на таблицу (DDL `:455`) покрывают новый столбец и запрос курсора.

### 4.5 Обратимость

- **Пока новых строк (`life IS NOT NULL`) нет — обратимо:**
  - `DROP INDEX af_*_life_seq_uq`, `DROP CONSTRAINT af_*_id_one`;
  - `ALTER COLUMN gen SET DEFAULT 0`;
  - `ADD CONSTRAINT af_*_pk PRIMARY KEY USING INDEX af_*_legacy_uq` — индекс btree, неполный, без выражений; SET NOT NULL на `gen` при этом сделает полный проход (ALTER TABLE, ADD table_constraint_using_index);
  - `DROP COLUMN life`.
- **После первой строки новой прошивки — необратимо без потери.** У новых строк `gen` = NULL. Откат потребовал бы назначить им `gen` (UUIDv8-свёртка, §7) или удалить их.

### 4.6 Новая установка

- `atomfast_pg_schema.sql` получает то же целевое состояние: `life uuid NULL`, `gen integer NULL`, оба уникальных индекса, CHECK.
- Функции `af_ingest`, `af_commit_cursor`, таблицы `af_cursor`, `af_gap`, `af_import_log` не меняются: это старый путь с `gen`, для сборщика.

## 5. Совместимость и порядок обновления

| Прошивка → база | Поведение |
|---|---|
| старая → мигрированная | Работает: `gen` задан, `life` = NULL, арбитр — `(hwid,ring,gen,seq)`. Ошибки прежнего механизма остаются у старой прошивки |
| новая → не мигрированная | `INSERT` с `life` → 42703. Кольцо останавливается (`af_pg_plan.h:252`), данные копятся на плате (до 11,9 сут сырых при одном буфере). «Установить соединение» заранее отказывает с понятной причиной. После миграции — «сохранить» (`af_pg.c:1297`), отправка продолжается без потерь, если кольцо не переполнилось |
| новая → мигрированная | Целевой режим |

**Порядок:** 1) резервная копия; 2) `af_migrate_life.sql`; 3) OTA новой прошивки (обработчик выключения сохраняет курсор e16j, из него берётся «пол»); 4) на плате — «установить соединение».

## 6. Доставка целиком

1. **Источник:** запись получает `(life, seq)` в момент помещения в кольцо, `seq` = позиция. Номер не меняется до базы и не выдаётся повторно (§3.2).
2. **Сессия:** вход → на каждое кольцо запрос верхней отметки базы (§3.3) → пачки строго по возрастанию `seq`, по одной инструкции.
3. **Атомарность пачки:** одна инструкция = одна неявная транзакция; при ошибке откатывается целиком (протокол, §53.2.2.1). При обрыве связи транзакция откатывается. Одиночная инструкция вне блока может успеть зафиксироваться (§53.2.9) — это закрывает идемпотентность.
4. **Подтверждение:** `CommandComplete` `INSERT 0 n` — счёт только вставленных (INSERT, «Outputs»). Курсор в ОЗУ сдвигается после `ReadyForQuery`; при ошибке сессия заканчивается.
5. **Повтор:** следующая сессия заново спрашивает верхнюю отметку. Строки, уже записанные базой, уходят повторно и отбрасываются `ON CONFLICT (life,seq) DO NOTHING`.
6. **Потери видимы:**
   - дыра `seq` внутри одной жизни = вытеснено до отправки либо строка отбракована платой;
   - счётчики `lost` и `s_inv_total` на плате.

## 7. Служебная утилита восстановления из CSV

- **Формат CSV платы.** Префикс `mac,seq,epoch,` (`af_hist_query.h:311`) становится `mac,life,seq,epoch,`.
  - `life` — UUID текстом.
  - Вещественные поля в новом служебном формате — `%.9g`; сейчас `%.6g` (`af_rec.h:220-226`). Девяти значащих цифр достаточно для точного восстановления float32.
  - Перед выгрузкой — `af_pfs_flush_now()`, чтобы в CSV не попал несброшенный хвост: его номер может выдаваться повторно (§3.2).
- **Загрузка новых CSV (есть `life`):**
  1. `\copy` во временную таблицу;
  2. `INSERT INTO af_raw (life,seq,ts,epoch,hwid,…) SELECT s.life, s.seq, to_timestamp(s.ts), s.epoch, h.id, … FROM st s JOIN hardware h ON h.mac = s.mac::macaddr WHERE s.ts <> 0 AND NOT EXISTS (<совпадение со старой строкой>) ON CONFLICT (life,seq) DO NOTHING`;
  3. `<совпадение со старой строкой>` = `SELECT 1 FROM af_raw r WHERE r.life IS NULL AND r.hwid = h.id AND r.ts = to_timestamp(s.ts) AND r.c2s = s.pulses_2s AND abs(r.dose - s.dose_msv) <= 1e-5*greatest(1,abs(s.dose_msv))`. Индекс `(hwid, ts)` есть (DDL `:61`). Неизвестный MAC сначала регистрируется через `af_hwid`.
  - Повторный импорт того же файла даёт 0 вставок.
  - Так возвращаются и записи, вытесненные до отправки, и записи, стёртые сбросом, если CSV снят до этого.
- **Старые CSV e16j (без `life`):**
  - синтетический `life` = UUIDv8 из `md5(mac||':'||epoch)` с цифрой версии 8. RFC 9562 §5.8: уникальность «implementation specific»; с UUIDv4 платы не пересекается, потому что у них другая цифра версии;
  - проверка совпадения по содержимому идёт против **всех** строк (старых и новых) — идентичность старых CSV ненадёжна, это и есть корень.
- **Строки старого механизма** остаются как есть (`life` NULL, `gen` задан). Строки, потерянные e16j из-за совпадения ключей (сценарий б), возвращаются этой же утилитой из CSV или кольца платы: проверка содержимого не даёт задвоить уже записанное.
- **Отчёт утилиты:** прочитано / вставлено / пропущено по ключу / пропущено по содержимому / отвергнуто CHECK.

## 8. Самопроверка по сценариям

Учёт: «потеряно» и «дублей» — по вине механизма доставки. Неотправленное, которое уничтожило само стирание, и несброшенный хвост ≤ 300 с при обрыве питания (R-A1) указаны отдельно. Они есть в любом варианте.

| Сценарий | Ход | Потеряно | Дублей | Остановок для решения человека |
|---|---|---|---|---|
| а. Три полных стирания подряд при наполненной базе, обрывы питания, в т.ч. до первой отправки | Каждое стирание → новый `life`, `seq` с 0. Совпадение с прошлыми жизнями исключено (9,4·10⁻³²). Обрыв до первого сброса: `life.bin` ещё не записан либо пуст по данным — новая или та же жизнь, отправленного нет. Обрыв после отправки: отправлено только сброшенное (§3.2) | 0 | 0 | 0 (диалог 2.2.1 — информационный, по букве ТЗ) |
| б. На e16j уже был полный сброс; затем миграция и обновление | Строки обеих старых жизней — с `gen`, не трогаются. «Пол» = `acked+1` из курсора e16j. Новые записи идут под `life`. Строки, потерянные e16j раньше, возвращает утилита (§7) | 0 новых (прошлые потери e16j — см. «не установлено») | 0 | 0 |

| г. Стёрты только настройки (NVS) | `life.bin` и `seq` целы. Тот же дозиметр: очистка не требуется благодаря MAC владельца (§3.1 п. 6). Флаг связи сброшен → «установить соединение» → отметка из базы | 0 (без доработки MAC — неотправленный хвост) | 0 | 0 |
| д. Отформатирован только раздел данных | NVS цел, флаг true. Новый `life` при первом сбросе, отправка продолжается без диалога | 0 | 0 | 0 |
| е1. Та же база по другому адресу | Отметка из базы → продолжение | 0 | 0 | 0 |
| е2. Другая база с данными | Своего `life` там нет → уходит всё кольцо (в этой базе этих строк нет). Чужие строки не задеты | 0 | 0 | 0 |
| е3. Пустая база | Нужна схема (42P01 → кольцо стоит, данные копятся); после применения DDL уходит всё кольцо | 0 | 0 | 0 (установка схемы — штатная настройка) |
| ж. Откат часов назад | `ts` не входит в ключ. Строки с `ts` вне CHECK отбраковываются, как и сейчас (DDL `:50`) | 0 | 0 | 0 |
| з. Две платы, один дозиметр | Одинаковый `hwid`, разные `life` — конфликтов нет | 0 | 0 по ключу | 0 |

**Итог: потеряно 0, дублей 0, остановок 0.**

Оговорки:
- е3: применить схему к пустой базе — штатный шаг настройки, ошибкой не считаю.
- з: при одновременном приёме одного дозиметра двумя платами каждое измерение окажется в базе дважды под разными `life` (см. «не установлено»). Это видно в `af_dup_suspects`.
