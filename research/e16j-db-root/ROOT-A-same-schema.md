Дата: 2026-11-14. Код: `<репозиторий прошивки>`, HEAD `a27d2aa` (ветка `t133-s1` поверх e16l-m1); версия заказчика — ветка `e16j-ota-auth` (`0bb9001`), читалась через `git show`. Схема: `atomfast_pg_schema.sql (схема БД, в этой папке не приложена)` (далее DDL). Требования: замечания заказчика к 0.1.0-e16j (issue #1) (далее ТЗ), раздел 2.
Граница: ключ `(hwid, ring, gen, seq)`, типы и функции DDL не меняются; добавляются только запросы чтения. Меняется только прошивка. Критерий владельца: риск × значимость × цена; редкое и малозначимое — в «принятые риски».

## 0. Резюме

- **Механизм.** Ключ записи в базе = `(hwid, ring, gen, seq)`, где `seq` — уже существующий номер записи в кольце, а `gen = base + lgen`. `lgen` («поколение записи») назначается при записи измерения в кольцо, хранится по прогонам (таблица прогонов в ОЗУ + поле `epoch` заголовка сегмента на флеше) и после этого не меняется. `lgen` растёт при каждой загрузке и при очистке, сквозь форматирование раздела данных — за счёт копии в NVS. `base` — одно число на плату. Оно задаётся только при «установить соединение» (п. 2.2.4) как `max(gen в базе) + 1 − min(lgen в буферах)`, одной атомарной записью NVS. Этим поднимается поколение сразу всех записей во всех трёх буферах, данные на флеше не переписываются.
- **Стандартный приём.** Стабильный идентификатор у источника + идемпотентный приёмник (`ON CONFLICT DO NOTHING`) + повтор «хотя бы один раз» по курсору. Поколение отделяет номера, переиспользованные после потери состояния, как «quiet time» в TCP (RFC 9293 §3.4.3).
- **Самопроверка по 7 сценариям (13 ветвей).** Из-за доставки потеряно 0, дублей 0, внештатных остановок 0. Исключения:
  - (е2) смена реквизитов на чужую базу с данными: 1 остановка, если принять автосверку (решение Р3); без неё — тихая потеря совпавших строк;
  - (г) сброс настроек: повторный выбор дозиметра стирает неотправленные сырые записи и агрегаты (это существующее поведение, с подтверждением пользователя).
  
  Потери из-за свойства буфера (обрыв питания до сброса на флеш, ≤300 с) учтены отдельно.
- **Цена.** Прошивка — около 350 строк (оценка), тесты — около 300. PSRAM — 1 632 Б на таблицу прогонов. NVS — +1 запись при каждой загрузке. Формат сегмента и записи **не меняется**: версия 1, совместим с e16j и e16l-m1 в обе стороны. Плата за это — один недозаполненный сегмент на каждую загрузку.

## 1. Корень — подтверждение по коду

- `gen` берётся из эпохи кольца в момент отправки: `gen = (int32_t)epoch` (`main/af_pg.c:838-844`). Эта же эпоха пишется в курсор (`:826`, `:876`, `:987`). У заказчика то же самое: `git show e16j-ota-auth:main/af_pg.c:830-834`.
- Эпоха растёт при каждой загрузке: `boot_epoch = epoch_load() + 1` (`main/af_persist_fs.c:387`). Восстановление берёт максимум заголовков + 1 (`main/af_persist.h:243-249`) и применяет его ко всему кольцу (`af_persist_fs.c:340`, `af_persist.h:267-274`). У кольца одна эпоха на всё содержимое (`main/af_ring.h:25`), у отдельной записи эпохи нет.
- Поэтому одна и та же запись при повторной отправке после загрузки получает другой `gen`. Курсор с «чужой» эпохой прошивка «усыновляет» (`af_pg.c:801-804`), а `af_push_plan` при смене эпохи начинает с самой старой записи (`main/af_push.h:499-501`). Всё это следствия, а не исправление причины.
- Переиспользование `seq` реально. Кольцо сбрасывается на флеш раз в 300 с или при 1 200 записях (`af_persist.h:23-24`). После обрыва питания `seq` продолжается с конца флеша (`af_persist.h:267-271`). Номера несохранённого хвоста выдаются новым измерениям повторно, а курсор при этом может быть впереди.
- После стирания раздела данных `epoch.bin` отсутствует, и `epoch_load()` возвращает 0 (`af_persist_fs.c:160-166`). Значит, эпоха начинается заново с 1, `seq` — с 0, и ключи `(hwid, ring, 1.., 0..)` совпадают со строками прошлой жизни. `ON CONFLICT DO NOTHING` (`main/pg_batch.c:424`) молча выбрасывает новые строки.

## 2. Идентификатор записи

### 2.1 Состав

- `seq` — номер в кольце, назначается при `af_ring_push` (`af_ring.h:59-85`). Уже стабилен: восстанавливается с флеша и при очистке не сбрасывается — очистка сохраняет `seq` (`af_persist_fs.c:824`, `:869-878`).
- `lgen` (uint32) — поколение записи, назначается при записи в кольцо значением текущей эпохи кольца. По существу это существующая `ring->epoch`, но привязанная к записи, а не к моменту чтения.
- `base` (int32) — смещение поколения, одно на плату, общее для трёх колец.
- `gen` в базе = `base + lgen`. Проверка `1 ≤ gen ≤ 2^31−1` (тип `integer`, DDL `:35`). Вне диапазона — остановка кольца с ошибкой, а не урезание.
- Инвариант: внутри одного `(base, lgen)` номер `seq` не повторяется. Новый `lgen` открывается при каждом событии, после которого `seq` может повториться или начаться заново:
  - загрузка (переиспользование несохранённого хвоста);
  - очистка (`af_pfs_clear`, эпоха = максимум + 1, `af_persist_fs.c:837`);
  - форматирование или стирание раздела данных (`seq` с 0).
  
  Других мест, где меняется `epoch`, в коде нет: grep `epoch = ` и `af_ring_clear` дал только `af_persist_fs.c:210/304/340/876`.

### 2.2 Где хранится `lgen` записи

- **ОЗУ.** Таблица прогонов на каждое кольцо: `{first_seq, lgen}` по 8 Б. Новая строка добавляется, когда `lgen` следующей записи отличается от последнего прогона. Строки, целиком вытесненные из кольца, удаляются. Поиск `lgen(seq)` — бинарный, под тем же мьютексом, что `af_store_read`.
- **Флеш.** Один сегмент = один `lgen`, значение лежит в существующем поле заголовка `epoch` (байты 16–19, `af_persist.h:52-55`). Для этого достаточно двух изменений:
  1. После восстановления не дописывать в последний сегмент прошлой загрузки: `k->cur_open = 0` вместо `p.append_last` (`af_persist_fs.c:351`). Первый сброс после загрузки откроет новый сегмент с `epoch = ring->epoch` (`:437-449`).
  2. При очистке переписать таблицу прогонов в том же захвате мьютекса, где правится кольцо (`af_persist_fs.c:863-878`), — это закрывает P6.
  
  При восстановлении таблица прогонов строится из заголовков загружаемых сегментов (`s_info[i].epoch`, `af_persist_fs.c:292`).
- **Монотонность `lgen` сквозь форматирование раздела данных (P3).** Эпоха загрузки = `max(epoch.bin, максимум заголовков, копия в NVS) + 1`. Копия в NVS (ключ `pg_ehw`, 4 Б) пишется при каждой загрузке и при очистке до первой записи в кольцо. Без неё после `format_if_mount_failed = true` (`af_persist_fs.c:79`) или ручного форматирования `lgen` начнётся с 1, и вернётся P2 — без всякого подтверждения пользователя.
- **`base`.** Хранится в двух местах: в NVS одним блобом `{ver, base, flag_connected}` и в файле `/storage/h/pgbase.bin` (8 Б: значение и его инверсия, как `epoch.bin`, `af_persist_fs.c:159-178`).
  - Порядок записи: сначала NVS, затем файл.
  - При загрузке главным считается NVS. Если файл расходится с NVS — файл перезаписывается.
  - Если в NVS блоба нет, а файл есть: `base` известен, флаг = false (случай «сброс настроек»).
  - Если нет ни того, ни другого: `base` неизвестен.
  
  Для NVS прерванная запись теряет только новое значение («should not result in loss of data, except for the new key-value pair if it was being written at the moment of powering off», ESP-IDF NVS, раздел «Security, Tampering, and Robustness»).

### 2.3 Формат и совместимость

- **Запись в кольце** (сырые 20 Б, агрегаты 28 Б, среда 14 Б; `main/af_rec.h:12-13`, `main/af_env.h:13`). У сырых и агрегатов свободен ровно 1 байт (`af_rec.h:90`, `:157`), но декодер требует в нём 0 (`:101`, `:168`). Хранить `lgen` в записи нельзя без смены формата и без отказа старых прошивок читать её. Поэтому `lgen` хранится по прогону, а не в записи, и **формат записи не меняется**.
- **Заголовок сегмента** остаётся версии 1 (`AF_SEG_VER 1`, `af_persist.h:12`, проверка `:69`). Байты 24–29 по-прежнему нули (`:60`). Меняется только правило: «один сегмент — один `lgen`».
- **Сегменты e16j/e16l-m1 при обновлении без стирания** читаются как есть (формат тот же: `git show e16j-ota-auth:main/af_persist.h:12,40,60,69`; `git diff e16j-ota-auth HEAD` по `af_persist.h` и `af_rec.h` пуст). В старом сегменте могут лежать записи нескольких загрузок: раньше была дозапись `append_last`. Они получат `lgen` = эпоха заголовка. Это безопасно: при миграции (§4.4) все неотправленные записи поднимаются выше максимума базы, а отправленные лежат за курсором и повторно не уходят.
- **Откат на старую прошивку.** Сегменты читаются: формат тот же. Поведение старой прошивки при отправке не анализировалось (вне задачи).

### 2.4 Память (расчёт: скрипт `локальный скрипт пересчёта, не публикуется`, вывод — ниже)

- Кольца при текущих константах (`main/af_store.h:10-14`, `af_ring.h:190-244`): сырые 181 491, агрегаты 20 160, среда 40 320 записей. На флеше хранится 116×1 600 = 185 600, 41×512 = 20 992 и 41×1 024 = 41 984 записей (`af_persist.h:17-22`). Флеш покрывает кольцо целиком по всем трём видам.
- Прогонов в кольце не больше, чем сегментов на флеше плюс 2 (текущий прогон и очистка). Отсюда 118 + 43 + 43 = 204 строки × 8 Б = **1 632 Б PSRAM**. При динамическом размере буферов (ТЗ п. 1.2) размер таблицы = `keep + 2` на кольцо: при 32 МБ это порядка нескольких КБ. Если таблица всё же переполнится (без флеша это невозможно, с флешем — только при ошибке расчёта), самый старый прогон вытесняется из кольца и учитывается как `dropped`.
- ОЗУ кроме PSRAM: `base` и флаг — 8 Б. Курсор остаётся прежнего размера: поле `epoch` курсора (`af_push.h:429-433`, блоб 48 Б, `af_pg.c:53`) теперь хранит `lgen` подтверждённой записи.
- Флеш:
  - +1 файл 8 Б;
  - плата за правило «один сегмент — один `lgen`»: в среднем половина сегмента на каждую загрузку. Это ≤0,86 % истории сырых и ≤2,44 % агрегатов и среды на флеше за загрузку (1/keep). В пересчёте на время: сырые — сегмент 1 600 × 2 с ≈ 53 мин, агрегаты — 512 × 60 с ≈ 8,5 ч.

## 3. Доставка — правила целиком

1. **Источник.** Запись получает `(lgen, seq)` при записи в кольцо. В базу она уходит с `gen = base + lgen`, на каждой попытке одинаково. `gen` теперь задаётся построчно: упаковщик пишет его в поле `epoch` CSV-префикса через функцию «gen по seq» (`af_push_pack`, `af_push.h:927`). `pg_csv_fill` берёт `row.gen` и `row.epoch` из этого поля, а не из параметра (`main/pg_csv.c:153`, `:246`, `:258`). Блок `af_pg.c:838-844` удаляется. Колонка `epoch` в базе становится равной `gen`; у строк e16j так было и раньше. HTTP-путь `af_push` получает `NULL` вместо функции и шлёт прежнюю эпоху кольца.
2. **Приёмник.** Многострочный `INSERT … ON CONFLICT (hwid,ring,gen,seq) DO NOTHING` (`pg_batch.c:275`, `:424`) — уже идемпотентен. Одна пачка = один оператор в простом запросе, то есть неявная транзакция: пачка вставляется целиком или не вставляется вовсе (PostgreSQL 17, §53.2.2.1, §53.2.9).
3. **Курсор** = ключ последней подтверждённой записи `(lgen, seq)` на кольцо. Начало отправки:
   - курсор недействителен → самая старая запись;
   - запись `seq = acked` есть в кольце и её `lgen` равен курсорному → `acked + 1`;
   - `acked` вытеснен, а самая старая запись относится к тому же `lgen` → самая старая, `lost = oldest − acked − 1`;
   - иначе → первая запись первого прогона с `lgen` больше курсорного, а если такого прогона нет — самая старая.
   
   Правило «при сомнении — с самой старой» безопасно, потому что повтор идемпотентен. Цена — только трафик. Блок «усыновления» `af_pg.c:801-804` удаляется.
4. **Подтверждение.** Курсор сдвигается только после `CommandComplete` + `ReadyForQuery` и проверки числа строк (`af_pg.c:954-999`). Если ответа нет, пачка повторяется с теми же ключами. По §53.2.9 строки могли уже зафиксироваться — повтор их пропустит.
5. **Запись курсора в NVS** — как сейчас: не чаще раза в 30 с (`af_pg.c:994`) и в обработчике `esp_restart` (`:1210-1215`). Отставание курсора после обрыва питания безопасно: повтор уходит с теми же ключами. Обработчик выключения вызывается только при `esp_restart()` (ESP-IDF, «Miscellaneous System APIs», Software Reset). При обрыве питания и панике действует п. 4.
6. **Кольцо переиспользует `seq` после обрыва.** Новые записи после загрузки получают новый `lgen`, поэтому их ключи не совпадают со строками несохранённого хвоста, который мог уже уйти в базу. Сам хвост в базе остаётся, то есть не теряется.
7. **Обнаружение (P8).** Счётчик пропущенных строк `s_skip_total` (`af_pg.c:981`) показывается в статусе. Рост пропусков без повторов — признак чужого писателя.

## 4. Сверка при подключении

### 4.1 Запросы (только чтение; `af_writer` имеет `SELECT`, DDL `:455`)

```sql
-- Q1: наибольший gen во всей базе (все приборы, три таблицы). NULL = база пуста.
SELECT max(x.g) FROM hardware h CROSS JOIN LATERAL (
  SELECT (SELECT gen FROM af_raw WHERE hwid = h.id AND ring = 0 ORDER BY gen DESC, seq DESC LIMIT 1) AS g
  UNION ALL SELECT (SELECT gen FROM af_agg WHERE hwid = h.id AND ring = 1 ORDER BY gen DESC, seq DESC LIMIT 1)
  UNION ALL SELECT (SELECT gen FROM af_env WHERE hwid = h.id AND ring = 2 ORDER BY gen DESC, seq DESC LIMIT 1)
) x;

-- Q2: последняя строка этого прибора по каждому кольцу ($H — hwid из af_hwid(mac), af_pg.c:716; целое подставляется литералом).
SELECT 0, gen, seq, extract(epoch FROM ts)::bigint FROM (SELECT gen, seq, ts FROM af_raw WHERE hwid = $H AND ring = 0 ORDER BY gen DESC, seq DESC LIMIT 1) a
UNION ALL SELECT 1, gen, seq, extract(epoch FROM ts)::bigint FROM (SELECT gen, seq, ts FROM af_agg WHERE hwid = $H AND ring = 1 ORDER BY gen DESC, seq DESC LIMIT 1) b
UNION ALL SELECT 2, gen, seq, extract(epoch FROM ts)::bigint FROM (SELECT gen, seq, ts FROM af_env WHERE hwid = $H AND ring = 2 ORDER BY gen DESC, seq DESC LIMIT 1) c;
```

- Оба запроса работают по первичному ключу `(hwid, ring, gen, seq)`. Равенство по ведущим столбцам плюс обратный проход, `ORDER BY … DESC LIMIT 1`, дают первую строку без просмотра остальных (PostgreSQL 17, §11.3 и §11.4). Q1 делает по 3 таких поиска на строку `hardware`.
- `ts` пишется как `to_timestamp(<целые секунды>)` (`pg_batch.c:219`, `:321`), поэтому сравнение с `ts` записи на плате точное.

### 4.2 Термины

- **Пустая база** — Q1 вернул NULL.
- **Своя строка** для кольца r. Q2 дал `(g*, s*, ts*)`, `base` известен, и в кольце есть запись с `lgen = g* − base`, `seq = s*` и тем же `ts`.
- **Строки базы старше буфера** — `(g*, s*)` лексикографически меньше ключа самой старой записи кольца `(base + lgen_oldest, seq_oldest)`.
- **Конфликт** — у этого прибора есть строки (Q2 не пуст хотя бы по одному кольцу), и хотя бы для одного такого кольца не выполнено ни «своя строка», ни «строки старше буфера», либо `base` неизвестен. Это значит: в базе могут быть ключи, которые совпадут с ключами наших неотправленных записей.

### 4.3 Решение при нажатии «установить соединение» (ТЗ 2.2.1–2.2.5, 2.2.8)

`Lmin` — наименьший `lgen` среди записей всех трёх колец (если кольца пусты — текущая эпоха).

1. **Пустая база** → `base := 1 − Lmin`, если он неизвестен. Курсоры сбрасываются, флаг = true, без вопроса (2.2.5).
2. **Нет конфликта** → флаг = true без вопроса (2.2.8).
   - Если `base` неизвестен: `base := Q1 + 1 − Lmin`. Это новая плата или новый прибор в общей базе; подъём выше всей базы исключает совпадения навсегда.
   - Для колец с «своей строкой» курсор := ключ этой строки (снимает 30-секундное отставание курсора). Для остальных колец курсор сбрасывается.
3. **Конфликт** → предупреждение 2.2.1.
   - «Да» → `base := Q1 + 1 − Lmin`, курсоры сбрасываются, флаг = true (2.2.4: поднято поколение всех записей во всех буферах; отправленные ранее повторно не нужны, неотправленные уходят под новыми `gen`).
   - «Отмена» → флаг = false, `base` не меняется (2.2.2).
4. **«Разорвать связь»** (2.2.7) → флаг = false, курсор сразу записывается в NVS, `base` не меняется.
5. **Смена реквизитов при флаге = true** (2.2.6; рекомендация Р3). Сразу выполняется та же сверка без диалога. Нет конфликта → работа продолжается. Конфликт → флаг = false и предупреждение (1 остановка, P5). Если Р3 не принят, действует буква 2.2.6: курсоры сбрасываются как сейчас (`af_pg.c:1304-1310`), и строки с совпавшими ключами в чужой базе молча пропускаются.

### 4.4 Автосверка после обновления (миграция P4)

- Признак миграции: в NVS есть настройки PG (`pg_cfg`), но нет блоба `base` и нет файла `pgbase.bin`.
- Действие в первой сессии, без диалога: `base := max(Q1, 0) + 1 − Lmin`. Курсоры сохраняются: `acked` остаётся, `lgen` курсора := `lgen` прогона, в котором лежит `acked`. Флаг := (отправка была включена).
- Обоснование:
  - курсор относится к той же базе: при смене реквизитов он сбрасывается (`af_pg.c:1304-1310`);
  - всё, что за курсором, уходит под `gen` выше всей базы, поэтому совпадений нет;
  - всё, что до курсора, повторно не отправляется;
  - OTA перезагружает через `esp_restart`, курсор при этом сохраняется (`af_pg.c:1210-1215`), так что окно «отправлено, но не подтверждено» = 0.
- Если миграция идёт после обрыва питания на старой прошивке, окно ≤30 с отставания курсора даёт единицы дублей. Принято, видно в `af_dup_suspects`.

## 5. Восстановление пропущенных строк из CSV (служебная утилита)

- **Что есть сейчас.** Расширенный CSV (`ext=1`) начинается с `mac,seq,epoch` (`af_hist_query.h:325`, разбор в `pg_csv.c:222-224`). При этом `epoch` — эпоха кольца **в момент выгрузки** для всех строк (`af_history_http.c:220`, `:247`, `:274`), а не поколение записи. Обычный CSV не содержит `seq` вовсе. Однозначного ключа в текущей выгрузке **нет**.
- **После изменения.** Выгрузка `ext=1` пишет в поле `epoch` `gen` записи (`base + lgen`), то есть ту же функцию, что и отправка (§3 п. 1). Ключ строки CSV = `(af_hwid(mac), ring по виду файла, gen, seq)` — тот же, что в базе.
- **Утилита.**
  1. Режет файл на участки с одинаковым `gen` и подряд идущими `seq`.
  2. Для каждого участка: `af_stage_prepare()` → `COPY af_stage FROM STDIN CSV` → `af_ingest(ring, hwid, gen, gen, first_seq)`.
  
  `af_ingest` нумерует `seq = p_first_seq + (ord − min(ord))` (DDL `:209`, `:306`), поэтому разрыв в `seq` обязан начинать новый участок. Вставка идёт с `ON CONFLICT DO NOTHING` (DDL `:295`, `:323`, `:344`). Повторный импорт того же файла безвреден, уже переданные платой строки пропускаются.
- **Без потерь довносятся:**
  - строки, стёртые сбросом;
  - строки, вытесненные до отправки (если файл выгружен до вытеснения);
  - строки, отброшенные чужим ключом.
  
  Условие: файл выгружен новой прошивкой при уже установленном `base`.
- **Ограничения.**
  - CSV, выгруженный до «установить соединение» или до подъёма `base`, несёт прежний `gen`. Импорт такого файла даст дубли по содержимому (P11), их видно в `af_dup_suspects` (DDL `:433-438`).
  - Старые CSV (e16j/e16l, P12) однозначного ключа не имеют. Возможен только импорт с отбором `NOT EXISTS` по `(hwid, ts, dose, doserate, c2s)` под отдельным отрицательным `gen` на каждый импорт. Это правило утилиты, схема не меняется.
  - Строки с `ts` вне [2020-01-01, 2100) прошивка не шлёт (`pg_batch.c:155`, `:209`), а DDL их отвергает (`:50`). Их нет и в результате импорта.

## 9. Первоисточники

- PostgreSQL 17, `INSERT`, раздел «ON CONFLICT Clause»: «ON CONFLICT DO NOTHING simply avoids inserting a row as its alternative action». Раздел «Outputs»: в теге `INSERT oid count` «count is the number of rows inserted or updated». https://www.postgresql.org/docs/17/sql-insert.html
- PostgreSQL 17, §53.2.2.1: несколько операторов в простом запросе выполняются «as a single transaction», то же для одиночного оператора вне блока («implicit commit or rollback»). §53.2.9: при обрыве оператор вне блока транзакции «might be committed before the disconnection is recognized». https://www.postgresql.org/docs/17/protocol-flow.html
- PostgreSQL 17, §11.4: при `ORDER BY … LIMIT n` с подходящим индексом «the first n rows can be retrieved directly»; индекс можно пройти в обратную сторону для `DESC`. §11.3: равенство по ведущим столбцам ограничивает просматриваемую часть индекса. https://www.postgresql.org/docs/17/indexes-ordering.html , https://www.postgresql.org/docs/17/indexes-multicolumn.html
- RFC 9293 (TCP), §3.4.3 «The TCP Quiet Time Concept»: узел, потерявший знание о последних номерах, рискует «sequence number overlap» со старыми дубликатами. Отсюда необходимость нового поколения после потери состояния.
- OASIS MQTT 3.1.1: §4.3.2 (QoS 1 — «at least once», возможны дубли) и §4.4 (после переподключения неподтверждённое повторяется с тем же Packet Identifier) — приём «повтор хотя бы раз со стабильным идентификатором». RFC 9110 §9.2.2 — идемпотентность делает повтор безопасным. Строки текстов — в `rag-1-delivery-keys-merge.md` §1, проблемы 2 и 3.
- ESP-IDF v5.3 (ESP32-S3), «Non-Volatile Storage Library», раздел «Security, Tampering, and Robustness»: при обрыве теряется только записываемая в этот момент пара. Раздел `nvs_commit`: изменения гарантированно на флеше только после `nvs_commit()`. https://docs.espressif.com/projects/esp-idf/en/v5.3/esp32s3/api-reference/storage/nvs_flash.html
- ESP-IDF v5.3, «Miscellaneous System APIs», Software Reset: обработчик `esp_register_shutdown_handler` вызывается перед перезапуском через `esp_restart()`; про панику и обрыв питания документ ничего не говорит. https://docs.espressif.com/projects/esp-idf/en/v5.3/esp32s3/api-reference/system/misc_system_api.html
- littlefs, README, «Power-loss resilience»: «All file operations have strong copy-on-write guarantees and if power is lost the filesystem will fall back to the last known good state»; «file updates are not actually committed to the filesystem until sync or close is called on the file». https://github.com/littlefs-project/littlefs/blob/master/README.md

## 11. Решения перед исполнением

- **Р1.** Предупреждать 2.2.1 только при конфликте по данным **этого прибора** (§4.2). Данные других приборов в общей базе обходятся подъёмом выше Q1 без вопроса. Буква 2.2.1 требует предупреждать при любой непустой базе.
- **Р2.** Повторное подключение к **своей** базе («своя строка») — без вопроса и без подъёма `base`. По букве 2.2.1 был бы вопрос, а «да» дало бы дубли всего буфера.
- **Р3.** Автосверка при смене реквизитов при флаге = true (P5): отступление от «проблема пользователя» в 2.2.6. Цена около 10 строк.
- **Р4.** Принять P9 или закрыть его хранением MAC дозиметра на разделе данных (зона BLE, около 15 строк).
- **Р5.** Автомиграция при обновлении (§4.4) без диалога, флаг выставляется по прежнему режиму отправки.
