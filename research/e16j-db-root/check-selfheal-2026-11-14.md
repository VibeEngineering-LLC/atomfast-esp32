## 2. Находки

### P0

Не найдено. Сценария гарантированной молчаливой потери первой записи при исправной БД и неизменных `base`/версии я не построил. Потери возможны только в P1-2 и только вне заявленного «потерь 0».

### P1

**P1-1. После подъёма `base` ключи уже отправленных строк меняются, поэтому полный повтор буфера даёт дубли сверх заявленного предела.**
Ключ — `gen = base + lgen` (RA:47-48). Подъём `base` (SH §3.1 шаг 2.5) переписывает `gen` ВСЕХ записей буфера, в том числе давно отправленных под старым `base`. Дальше любой законный полный повтор уходит под новыми ключами, `DO NOTHING` не срабатывает, сравнение не запускается (`ins == rows`). Пути: сброс курсоров при смене реквизитов на ту же базу при отклонённой Р3 (`af_pg.c:1295-1301`), `af_pg_reset` (`:1482-1492`), «установить соединение» после «разорвать связь» для кольца, у которого последняя строка в базе старше подъёма (Q2 даёт `g* < base'+Lmin`, это «строки старше буфера», курсор сбрасывается, RA:129-131,139-140), повторный импорт CSV (RA §5, там основа — стабильный `gen`). Ёмкость повтора — всё кольцо (до 181 тыс. сырых, RA:82). SH заявляет (е1) «Д=0» и «≤ одной пачки» (§0, §5) — это неверно после первого подъёма.
Правка: ввести кусочную `base` — список точек перелома {кольцо, первый неотправленный `(lgen,seq)`, `base'`}, не больше суточного предела; `gen(lgen,seq)` берёт `base` по точке перелома, поэтому уже отправленные строки сохраняют ключи. Либо хранить для запасного `gen` таблицу переселённых диапазонов. В §5 добавить сценарий «подъём → сброс курсоров/реквизиты/CSV-импорт» с замером дублей.

**P1-2. Три механизма молчаливой потери вне формулы «потерь 0».**
(а) §8 S3-а: строку, отвергнутую базой (23514 CHECK, 22xxx), «пропустить с учётом в `s_inv_total`». Это постоянная потеря валидной для прибора строки при несовпадении схемы и прошивки. SH §8 и RA:239 сами отмечают рассинхрон (HEAD шлёт `sht4x/bmp390/bmp58x`, DDL:137 их отвергает). В смешанной пачке (датчики чередуются, DDL:103) защита «отвергнуты все строки пачки» не срабатывает. В e16j (`pg_csv.c:123-126`) модели совпадают с DDL — условие HEAD, но правило остаётся механизмом тихой потери.
(б) Список сравниваемых столбцов `af_env` не выписан (SH §1.3, §7.2). Если в нём нет `sensor`, `model`, `hum_pct`, `press_pa`, `temp_c`, `flags`, возникает «ложное то же» → строка среды молча не досылается (DDL:112-118).
(в) Записи с `ts` вне [2020-01-01, 2100) не уходят никогда (`pg_batch.c:155,207-210`), а отсчёты до синхронизации времени кладутся в кольцо с `ts=0` (`af_store_core.h:78-81`, счётчик `ts0_samples`). Формула «потерь 0» в §0/§5 этого не оговаривает (оговорка есть только в §5 «что НЕ ловит»).
Правка: (а) пропуск только после N≥3 повторов в разные сеансы и с записью в журнал (`seq`, SQLSTATE, колонка из `COLUMN_NAME` ответа), счётчик «отвергнуто базой» в статусе; (б) выписать полный список из DDL:105-125 до реализации, мутационный тест на подмену каждого столбца; (в) в резюме и в таблице П заменить «потерь 0» на «потерь 0 при годных записях».

**P1-3. Тип в запросе сравнения зашит (`::real`); при иной колонке каждый повтор «другой».**
SH §2.2: `v.doserate::real`. Если у заказчика колонка `double precision`/`numeric` (DDL e16k не равен схеме заказчика на e16j, RA:3), `real(0.123457)` ≠ `0.123457` двойной точности: расхождение по КАЖДОЙ повторной строке → подъём `base` на каждой повторной пачке → массовые дубли (до суточного предела 24, дальше запасной `gen` на каждую повторную пачку).
Правка: при первом сеансе запросить типы (`SELECT atttypid::regtype FROM pg_attribute …` по трём таблицам); при отличии от DDL — режим «только счётчик, без подъёма» плюс видимое предупреждение; в тестах — стенд с колонкой `double precision`.

**P1-4. Перечень §8 неполон; часть «ожидания» — остановка по существу.**
Не названы: (1) `xTaskCreate` не удался — `s_running=0`, повторного запуска нет (`af_pg.c:1244-1247`, `main.c:103` вызывает `(void)af_pg_start()`): отправка не работает до перезагрузки; (2) `AF_PG_E_SCRAM_ITER` (число итераций сервера > `scram_iter_max` 100000, `af_pg.c:593,620`) и `AUTH_UNSUPPORTED` — бесконечный повтор без изменения исхода при смене настроек сервера; (3) детерминированные ошибки: S1 `PG_CSV_E_FORMAT` без `\n`, 42601 «ожидание с видимой ошибкой» (SH §8 S3-б) — повтор тех же данных даёт ту же ошибку, ничего не отправляется, кольцо вытесняется. Требование владельца «запись не встаёт» это нарушает, хотя SH считает «ожиданием».
Правка: добавить (1) в §8 с повтором создания задачи раз в 60 с; ввести общий счётчик «одна и та же ошибка N раз подряд без продвижения курсора» → переход на деление пачки/пропуск с журналом (после N) вместо вечного повтора; (2) пороговая правка `scram_iter_max` — до 1 000 000 с проверкой времени PBKDF2.

**P1-5. Подтверждение повтора целиком зависит от права `SELECT` у роли заказчика.**
Без права на столбцы сравнения запрос даёт 42501; по SH §8 S3-б это «повтор с backoff». Но курсор без сравнения не сдвигается (SH §3.1 шаг 1), значит каждая законная повторная пачка блокирует кольцо навсегда (до эвикции). Для `ON CONFLICT` нужен `SELECT` только на ключевые столбцы (URL sql-insert), поэтому роль с column-level `GRANT` вполне допустима и INSERT у неё работает.
Правка: если сравнение вернуло 42501 — одноразовое предупреждение и откат к поведению e16j (курсор вперёд, пропуски в счётчик) вместо блокировки; пробу права `has_column_privilege` выполнить при «установить соединение».

### P2

1. **Гонки записи блоба `base`.** Блоб содержит `flag` (SH §3.1 шаг 2.5; RA:65). Подъём пишет `{base', flag, …}` без перечитывания флага под `s_mtx`: «разорвать связь» (ТЗ 2.2.7) в окне подъёма воскресит флаг. Нет проверки `pg_fresh_locked` перед записью (реквизиты могли смениться, Q1 — из другой БД). Правка: read-modify-write блоба под `s_mtx` + проверка свежести сеанса.
2. **Размер запроса и сравнение при делении.** Резерв 64 Б (`pg_batch.c:283`) меньше хвоста сравнения (~400 Б, SH §6.2). Правка: при сборке сравнения использовать меньшую пачку (≤ cap − 512), а при ошибке сравнения половины — не двигать курсор.
3. **Подсчёт запросов (п. 16 таблицы)** и время сеанса 120 с (`af_pg_plan.h:36`): подъём с Q1 по трём таблицам × число приборов плюс сравнения могут съесть сеанс; нужна оценка времени Q1 на базе заказчика (SH §7.2 не измерено).
4. **Риск 2 (формат чисел) шире, чем `pg_fmt_f`.** Между версиями меняются и текстовые `af_*_csv` (звено до `pg_fmt_f`), и маппинг `kind/flags/model` (`pg_csv.c:123-129`). После OTA со сменой любого — «ложное другое» на каждой повторной пачке. Правка: в #REL-GATE добавить сверку CSV-вывода старой и новой версии на одном буфере (байт в байт) до выпуска.
5. **Схема e16k против базы заказчика на e16j.** Все выводы про права и типы сделаны по DDL e16k (`public-ddl`); версия DDL заказчика не сверена. Правка: запросить у заказчика `\d af_raw af_agg af_env` и `\dp` (без паролей) до реализации.
6. **Неподтверждённые факты** (таблица, п. 10-12, 33): проверить на стенде с реальным PostgreSQL 17 до принятия §3.1 — `DO NOTHING` с двумя кортежами одного ключа; видимость сравнения; поведение числовых литералов в `VALUES`.
7. **Остаточные проверки на мутацию (#SA-3).** SH §7.1 риск 4 верно называет «пустой `D`» главным риском; в план тестов добавить мутации именно этого запроса: подмена каждого сравниваемого столбца, `NULL` вместо значения, смена типа колонки, пустая таблица, дубль `seq` в одной пачке.

## 3. Ответы на отдельные вопросы задания

- **Признак «то же содержимое».** Для записей, неизменных после постановки в кольцо (п. 1) и при неизменных `base` и версии формата — подходит. Агрегаты после отправки не переписываются (п. 1). Часовые пояса не влияют (п. 3). Округление `pg_fmt_f` детерминировано (п. 4). Не подходит при подъёме `base` (P1-1), смене версии формата (P2-4), иной колонке (P1-3).
- **Запрос сравнения.** NULL-логика верна (п. 6); типы приводятся попарно (п. 7); ошибки: зашитый `::real` (P1-3), неполный список для env (P1-2б), зависимость от права SELECT (P1-5).
