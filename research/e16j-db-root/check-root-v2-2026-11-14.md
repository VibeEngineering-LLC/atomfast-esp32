## 0. Вывод

- Формула `gen = B + lgen` и условие непересечения жизней проверены и верны при верных часах и прогонах реже 1 в секунду. Сами ключи по коду уникальны внутри жизни (в том числе пустые кольца получают новый прогон на каждой загрузке, `af_persist_fs.c:210`).
- Находки ПР по существу закрыты или честно перенесены в риски. Но две правки второй редакции создают новые дефекты: правило п. 8 (закрепление прогона) вводит остановку отправки, которой в e16j нет, а подрезка снизу по «дате сборки» вредна и опирается на непроверяемую константу.
- Заявления «остановок без человека не добавляет» и «R4 требует двух грубых ошибок часов» неверны (П1-1, П1-2). Их нельзя нести заказчику в нынешнем виде.
- Механизмов во второй редакции меньше по хранимому (12 полей в двух местах → 4 поля в одном), но добавлены семь новых правил и состояний; три из них можно убрать без потери свойств (§5).

## 4. Прогон сценариев

| Сценарий | Результат по коду |
|---|---|
| Полное стирание | Новая жизнь, `lgen` с 1, `B' = T0' − lgen_hw'`. Диапазоны разнесены при верных часах. **Утечка:** при неверных часах (раньше `S`) обе жизни получают `T0=S`, диапазоны `[S−r, S+n]` совпадают, `seq` с 0 у обеих: массовое совпадение ключей, тихая потеря (П1-2). |
| Стирание только настроек (в т. ч. `wifi_manager.c:651-655`) | `B` из файла, `lgen` из `epoch.bin`; курсор и реквизиты потеряны, повтор кольца с теми же ключами → `DO NOTHING`. Режим PG возвращается в OFF (`af_pg_plan.h:382`), пока человек не включит. Дублей нет. |
| Форматирование только раздела данных, курсор цел | Файла нет → `B'`; метка не совпадает → повтор с самой старой. Верно. Неверно в окне «после OTA с e16j, до первой потребности»: курсор версии 1 без метки и по §1.5 переводится в версию 2 с меткой нового `B` (П2-4); при `acked` больше нового `head` записи молча пропускаются. |
| Обрыв питания: до записи временного файла | `B` нет, отправки не было — безопасно. |
| то же: между временным файлом и rename | остаётся лишний файл; следующая попытка перезаписывает. Безопасно. |
| то же: между rename и чтением | файл цел, отправка ещё не шла. Безопасно. |
| то же: ошибка записи/сверки | `B` в ОЗУ, отправка идёт, метка курсора от ОЗУ-`B`. После перезагрузки новый `B'`, курсор недействителен: всё кольцо уходит под новыми ключами, и так на каждой загрузке (П2-6). |
| то же: после rename, до сохранения курсора | курсор отстаёт, повтор с теми же ключами → `DO NOTHING`. |
| Несколько перезапусков подряд | `B` не меняется, `lgen` растёт. Каждый сброс с `pending>0` открывает новый сегмент (`cur_open=0`), а лишние уходят по `keep` (`af_persist_fs.c:468-472`): за 41 перезапуск стирается вся флеш-история агрегатов и среды, за 116 — сырых (П2-1). |
| Время появляется позже первой записи | Записи до этого с `ts=0` не уходят (как e16j). `B` по первому `time(NULL)≥1,7·10⁹`. Верно. |
| Время от браузера ошибается | Назад раньше `S` — подрезка до `S`, в нескольких жизнях одинаково (П1-2). Вперёд — `gen` выше, безвредно до совпадения с реальным временем. Внутри отрезка прошлой жизни — совпадения (R3). |
| Обновление с e16j | Ключи не пересекаются с e16j (граница >2,1·10⁸). Курсор v1 переводится при потребности; дубли при недействительном курсоре. Окно из строки «Форматирование» выше. |

## 5. Находки

### P0

Нет.

### P1

**П1-1. Правило п. 8 вводит остановку отправки, которой в e16j нет; фраза «Остановки нет» неверна.**
- Факт: граница плана до закрепления — `persisted_seq`. В режиме «только ОЗУ» `s_mounted=0`, сброс на флеш не выполняется (`af_persist_fs.c:376`, `:925`), `persisted_seq` остаётся 0, `epoch.bin` писать нельзя. При ошибке `fopen` в `flush_kind` (`:437-441`) `persisted_seq` тоже не растёт. По п. 8 всё несброшенное остаётся неотправленным.
- Противоречие: §1.4 прямо разрешает отправку с `B` в ОЗУ.
- Сценарий: стационарная плата с сетью; ошибка флеша (раздел заполнен, ошибки ввода-вывода) или сбой монтирования. e16j шлёт из ОЗУ, В2 молчит до исчезновения причины; кольцо перезаписывается — молчаливая потеря годных записей. Нарушает требование владельца 1 (отправка не встаёт без человека).
- Правка: п. 8 не применять при `!s_mounted`; при сбое записи `epoch.bin` и сегмента отправлять с пометкой «не закреплено» (счётчик `unanchored_sent` в статусе), а не ждать. Потеря ключа при обрыве питания тогда возможна, но это e16j-поведение и видимое.

**П1-2. Подрезка времени снизу вредна, оценка R4 неверна, а константа `S` ненадёжна.**
- Подрезка `T0 := max(T0, S)` сводит все неверные даты раньше `S` к одному значению. Реальные жизни всегда выше `S`, и от них подрезка не защищает. Без подрезки разные неверные даты дали бы разные `B`, одинаковые — только при «залипшей» дате.
- R4 «требует двух грубых ошибок» неверно: ПК с севшей батарейкой CMOS (2023–2025) или телефон с неверной датой в сети без NTP — одна коррелированная ошибка на все перепрошивки. Именно сеть без NTP заказчика проект не исключает (§6 п. 3). Результат: каждая перепрошивка той же платы в такой сети даёт ключи `[S−r, S+n]`, `seq` с 0 — молчаливая потеря первых `max(seq)` строк новой жизни. Это тот сценарий, ради которого затеяна работа (ТЗ 2.1), только с другим триггером.
- `S` из `git log -1 --format=%ct` (§1.2 п. 4): дата коммита с машины с неверными часами в будущем даёт `S` больше реального времени — подрезка снизу ставит **все** жизни парка в один `B` до наступления `S`. Резервного значения при сборке без `.git` проект не задаёт; при инкрементальной сборке CMake значение может быть старым. Бесплатной замены нет — проверить нельзя без сборочной среды заказчика.
- Правка: убрать `S` и `U = S+30 лет`; нижняя граница — уже существующие `1,7·10⁹` (иначе `ts` не ставится), верхняя — единственная `2³¹−1−2²⁴`. Тогда нет CMake, нет git, нет резервного значения. Для R4 оставить честную оценку «одна коррелированная ошибка», а решение Р-В2 принимать на ней.

### P2

**П2-1. Сегмент на загрузку × `keep` стирает флеш-историю при серии перезапусков; в рисках В2 этого нет.** `af_persist_fs.c:437-441` открывает новый сегмент при `cur_open=0`, `:468-472` удаляет старейший при превышении `keep` (`AF_SEG_RAW_KEEP 116`, `AF_SEG_AGG_KEEP 41`, `AF_SEG_ENV_KEEP 41`, `af_persist.h:17-22`). Корректный перезапуск сбрасывает остаток (`af_store.c:73-88`), так что 41 перезапуск с хотя бы одной записью стирает всю историю агрегатов и среды. РА (P7, §7) это знает и приводит способ (метка чистого выключения, ≈15 строк); В2 его не берёт и в риски не вносит. Правка: внести в §9 как риск и в §8 как ≈15 строк.

**П2-2. Два места назначения `B` без взаимного исключения; назначение из CSV опасно в поле.** Задача PG и обработчик CSV `ext=1` (`af_history_http.c:194`) вычисляют `T0` независимо: одновременный вход даёт два разных `B`, файл и ОЗУ расходятся. Назначение из CSV в AP-режиме берёт `T0` от телефона (§7 проекта): ровно тот сценарий, который отложен как «поле». Правка: один мьютекс и флаг «назначено»; лучше убрать CSV из потребностей — колонка `gen` пуста до первой отправки (потеря: CSV до первой отправки без `gen`).

**П2-3. `epoch.bin` пишется не атомарно, а теперь это опора п. 8.** `epoch_store` открывает `fopen(...,"wb")` (усечение) и пишет 8 байт (`af_persist_fs.c:169-178`); обрыв питания между усечением и записью даёт пустой файл, `epoch_load` возвращает 0 (`:157-165`), следующая загрузка начинает с `boot_epoch=1`. Для колец с данными заголовки сегментов компенсируют (`af_persist.h:243-249`); для колец без сегментов (первые минуты жизни, до первого сброса) номер прогона повторится при тех же `B` и `seq` с 0 — совпадение ключей, тихая потеря. Правка: запись через временный файл и rename (как для `pgbase.bin`), чтение и сверка — в той же функции.

**П2-4. Миграция курсора v1→v2 и общий кодек.** (а) Метка := `B` неизвестна на загрузке; до первой потребности курсор остаётся v1 и после форматирования раздела данных получает чужое `acked` (молчаливый пропуск до `acked`). (б) Зажим `acked > head−1` из `af_pg.c:793-795` в переводе не описан. (в) Кодек курсора общий с HTTP-отправкой (`af_push.c:73`, `:99`): версия 2 с меткой там никем не задана. Правка: переводить на загрузке с меткой «ждёт `B`» (0), принимать курсор только если `acked ≤ head` и `lgen ≤ lgen_hw`; для HTTP-пути писать версию 1.

**П2-5. `T0` из `ts` самой новой записи не учитывает прогоны после неё.** Если после этой записи было `m` загрузок без валидного времени, нижняя граница `T0 − r` уходит вниз на `m` секунд раньше начала жизни, то есть под конец предыдущей. Правка: `T0 := max(ts_новейшей, ts_новейшей + число прогонов после неё)` либо при этой ветке подниматься до `ts+r`. Обход от `head` назад по 181 491 записи под `s_mtx` (≈ десятки мс, не замерено) — ограничить N.

**П2-6. Дубли при незаписываемом файле не ограничены.** Строка 13: каждая загрузка при `base_unsaved>0` даёт новый `B`, курсор недействителен, всё кольцо (до 181 491 сырых строк) уходит заново под новыми ключами. Серия перезапусков = рост дублей без предела. Правка: счётчик и порог; при `base_unsaved` в предыдущей загрузке повтор кольца не начинать, пока файл не записан или оператор не подтвердил.

**П2-7. Расхождения в тексте.** `af_pg.c:268` (загрузка, не запись), `af_pg.c:972`→`:971`; «около 210» против §8; §4.1 «эпоха растёт только в restore»; `epoch` в базе = `lgen`, в CSV = `gen`, в РА = `gen` (§3 п. 1).

## 6. Сценарии молчаливой потери, дубля, совпадения и остановки (стационарная установка, сеть есть, одна плата на дозиметр)

1. **Остановка.** Раздел данных не монтируется или флеш отказывает: п. 8 держит границу `persisted_seq`, отправка стоит (П1-1).
2. **Совпадение ключей.** Сеть без NTP, время берётся с ПК с неверной датой раньше сборки: после каждой полной перепрошивки `T0=S`; ключи совпадают с прошлой жизнью, первые `seq` новой жизни молча отбрасываются `DO NOTHING` (П1-2). С подрезкой `S` в будущем — вся серия плат парка.
3. **Тихая потеря через `epoch.bin`.** Обрыв питания в момент усечения файла в первые минуты жизни (П2-3).
4. **Дубли.** Файл `pgbase.bin` не пишется: новый `B` на каждой загрузке, повтор кольца (П2-6). Миграция с недействительным курсором.
5. **Потеря истории.** Серия корректных перезапусков стирает флеш-историю (П2-1).
6. **Пропуск до `acked`.** OTA с e16j, затем форматирование раздела данных до первой потребности (П2-4).

Построить сценарий потери при верных часах, одной плате, исправном флеше и штатных событиях (полное стирание, стирание NVS, форматирование раздела с живым курсором, обрыв питания, серия перезапусков до 40, поздняя синхронизация времени, обновление с e16j при штатной миграции) **не удалось**: ключи уникальны по построению.
