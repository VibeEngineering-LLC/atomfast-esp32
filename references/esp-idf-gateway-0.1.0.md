# AtomFast Gateway на ESP-IDF, линия 0.1.0-e16* (e16g, e16h, e16j, e16k)

Новая основа шлюза, не обновление ESPHome-линии (`v0.9.x-s3` и ранее): код переписан на ESP-IDF 5.4, Web UI создан заново. ESPHome-линия остаётся в репозитории отдельно и не затрагивается. Релизы: [v0.1.0-e16g](https://github.com/VibeEngineering-LLC/atomfast-esp32/releases/tag/v0.1.0-e16g), [v0.1.0-e16h](https://github.com/VibeEngineering-LLC/atomfast-esp32/releases/tag/v0.1.0-e16h), [v0.1.0-e16j](https://github.com/VibeEngineering-LLC/atomfast-esp32/releases/tag/v0.1.0-e16j); контрольные суммы — [`version-history.md`](version-history.md). Шьётся прошивальщиком 0.7.3 и новее ([v0.7.3](https://github.com/VibeEngineering-LLC/atomspectra-waterfall-esp32-flasher/releases/tag/v0.7.3)): проект «AtomFast Gateway, ESP-IDF» в прежних версиях отсутствует.

Протокол прибора (13 байт, GATT) тот же: [`atomfast-onair-protocol.md`](atomfast-onair-protocol.md), официальный конспект — [`atomservice-ble-official-doc.md`](atomservice-ble-official-doc.md).

## 1. Архитектура

- Плата: ESP32-S3 N16R8 (16 МБ флеша, 8 МБ PSRAM). Фреймворк ESP-IDF 5.4, BLE-стек Bluedroid (только BLE), мощность передачи P20 (+20 dBm) задана явно; проверка — по сгенерированному `sdkconfig` (`CONFIG_BT_CTRL_DFT_TX_POWER_LEVEL_EFF` = 15), не по исходному конфигу.
- Собственные модули: BLE-шлюз к дозиметру, хранилище, веб-сервер, отправка в базу. Очередь BLE-пакетов: пакеты прибора читаются все (в тестовом замере 60 с: 30 пакетов, 0 потерь).
- **Три кольцевых буфера** в PSRAM с зеркалом на флеш (LittleFS): сырые отсчёты (пакет прибора), агрегаты (окно усреднения), отсчёты датчиков среды (BMP280: температура, давление). Формат сегментов двоичный, с контролем CRC16 и версией формата; запись помечена порядковым номером `seq`, у буфера есть эпоха `epoch`. Масштаб графика: шаг от 60 с на пиксель берёт агрегаты, меньше — сырые отсчёты.
- Обновление по воздуху (OTA) и запись домашней Wi-Fi сети при прошивке через прошивальщик; без заданной сети плата поднимает точку доступа для настройки (адрес по умолчанию `192.168.4.1`).
- Web UI: вкладки «Главная», «Показания», «Измерения», «Система» (хранилище, обслуживание, MQTT/Home Assistant, «База данных»); тёмная и светлая темы; график с двумя осями; значения с погрешностью («± %»). Вкладка «Измерения»: «Разовое», «Серия», «Из журнала», остановка по времени или по достигнутой погрешности, экспорт CSV.
- Очистка хранилища (сырые, агрегаты, среда, всё, журнал) — только после подтверждения с числом записей и вводом слова «стереть». Запросы, меняющие состояние платы, проверяются по заголовкам Host/Origin. Действия «Пересчитать агрегаты из сырых» нет (удалено до выпуска e16g).

### Выгрузка данных (CSV и опрос)

- Состояние кольца: `GET /api/history/status` (эпоха, голова, самая старая запись, число записей). Данные: `GET /api/history.csv?kind=raw|agg|env`.
- CSV имеет колонку `kind`; для сред — шапка `ts,kind,sensor,model,temp_c,hum_pct,press_mmhg,press_pa,flags`. В расширенном виде (`ext=1`) первыми идут `mac,seq,epoch`. Сырой байт флагов прибора сохраняется в колонке `flags`.
- Выгрузка из UI содержит только расширенный вид; отдельной настройки «включать ли MAC прибора» нет.

### Push-канал и раздел «База данных» (e16h)

Описано состояние e16h; в e16j плата пишет в PostgreSQL сама (раздел 7). В e16h плата не содержит клиента базы данных: она сама отправляет накопленную историю пачками по HTTP на приёмник в домашней сети, приёмник пишет в PostgreSQL.

- Раздел «База данных» на странице «Система» (между «MQTT / Home Assistant» и «Хранилище»): включение, адрес приёмника, порт, токен (только запись: показывается «задан / не задан», есть «Очистить сохранённый токен»), «Сохранить», «Проверить» (пробный запрос без данных), статус по трём буферам и «Сбросить позицию отправки» (с подтверждением; данные на плате не удаляются, пачки уйдут повторно).
- Эндпоинты платы: `GET /api/push` (состояние, токена в ответе нет), `POST /api/push` (патч настроек), `POST /api/push/test` (пробный запрос; результат берётся опросом `GET /api/push`, поле `test`), `POST /api/push/reset` (тело `{"confirm":true}`).
- Диапазоны настроек: порт 1–65535, токен 1–64 видимых символа ASCII без кавычек и `\`, период отправки 10–3600 с, строк в пачке 50–2000, ожидание ответа 2–30 с, непустой набор колец из `raw`, `agg`, `env`. Смена адреса или порта сбрасывает позицию отправки (другой приёмник — другая база).
- Запрос к приёмнику: `POST /ingest/<кольцо>` с телом CSV (пример: `/ingest/env`), заголовки `X-AF-*` (идентификатор прибора, эпоха, первый `seq` пачки; пробный запрос дополнительно `X-AF-Test: 1`) и токен. В каждой строке CSV есть `mac,seq,epoch`, поэтому повтор пачки приёмник отбрасывает по ключу.
- Состояние отправки: `off`, `idle`, `sending`, `error`; по каждому кольцу — число ожидающих строк, подтверждённый `seq`, последняя ошибка (`net`, `server`, `auth`, `bad_batch`, `too_big`, `proto`, `no_device` и др.). Приёмник отказал (401, неверный токен) — отправка останавливается до «Сохранить».
- Шифрования канала нет (TLS нет): токен и данные идут открытым текстом, плата предупреждает, если адрес не похож на домашний. Отправка по умолчанию выключена. Приёмник в релиз не входит.
- Если плата ещё не видела дозиметр, идентификатора прибора нет и отправка не стартует (`no_device`).

## 2. Настройки и ограничения

- Web UI открывается **без пароля**: плату держать только в доверенной домашней сети. Токен запросов, меняющих состояние, доступен любому устройству сети.
- Скорость главной страницы `/` (135 КБ, один файл с gzip): p95 в замерах 0,32–0,34 с при хорошем сигнале и 0,42–0,43 с при сигнале около −72 дБм; цель 0,35 с при слабом сигнале не достигнута. Время растёт с размером страницы (порядка 2 мс на КБ). Повторный заход по ETag/304 — около 0,1 с.
- Интервал BLE-соединения 45–100 мс и окно графика 5 мин отдельно не проверялись. Вёрстка под 375 px: горизонтальной прокрутки нет, но целевая область кнопок 40 px (ниже 44 px).
- Прошивка e16h из релиза через прошивальщик на реальной плате не проверялась (проверен предыдущий e16g: factory, затем «Обновление: сохранить настройки»; история не стёрлась, потому что запись factory без «полного сброса» раздел данных не трогает).
- Бит 3 флагов прибора и коэффициент погрешности: за 156 784 записи флаги всегда 0; «± %» считается как 100/√N (k = 1, примерно 67 %) без поправки на мёртвое время (для счёта выше 100 имп/с поправка нужна, на домашнем фоне порядка 18 имп/с не требуется).

## 3. Находка: Wi-Fi и BLE на одном радио (диагноз отклика платы)

Плата с работающим BLE отвечала на ICMP и HTTP медленнее, чем плата-эталон той же серии без BLE (другая прошивка), при том же уровне сигнала (−70…−72 дБм, разница 1–2 дБ). Модемный сон Wi-Fi исключён (`WIFI_PS_NONE` на обеих), процессор не нагружен (около 2 %).

| Показатель | плата с BLE | пробник без запуска BLE | эталон |
|---|---|---|---|
| ping 80 пакетов × 100 мс, число ответов > 50 мс | 14 из 80 | 0 из 80 | 0 из 80 |
| ответ 404, p90 до первого байта, мс | 62 | 9 | 10 |
| тривиальный `/healthcheck`, минимум, мс | 65 | 49 | не измерялся |

- Пилообразные задержки ICMP (рост на 10–20 мс за пакет до ≈57 мс и сброс) и кванты ≈55 мс исчезают, когда BLE не запускается (контроллер включён, сканирования и подключения нет). Гипотеза: временное разделение радио между Wi-Fi и BLE (coexistence), документация ESP-IDF описывает долю времени Wi-Fi порядка половины периода при подключённых Wi-Fi и BLE.
- **Не разобрано:** остаточный пол ≈50 мс на зарегистрированных маршрутах (пробник против 12–14 мс у эталона) остался и без BLE; отдельная гипотеза — окно TCP 5760 Б против 65535 Б у эталона — не проверялась.
- Ограничения вывода: одно измерение на одной плате в одном состоянии канала, повтор не делался; «контроллер включён без Bluedroid» не равно «BLE полностью выключен». Пробный образ в релиз не входил. Улучшение запланировано на следующую версию.

## 4. Методика проверки выпуска

Принятая для линии проверка перед релизом (результаты по e16g/e16h — в отчётах разработки, здесь только метод):

1. **Soak 60 мин** на живой плате с открытой страницей `/system`: ≈130 замеров, все ответы 200, `alloc_fail` и `rejects` равны 0, минимум свободной внутренней памяти не падает, аптайм растёт без перезагрузки.
2. **p95 страницы** по 30 запросам, с записью RSSI до и после каждого замера. Сравнение образцов допустимо только при сопоставимом RSSI; без записи RSSI вывод «прошивка быстрее» не принимается.
3. **Парное сравнение с эталонной платой** на одном канале (ping, 404, `/healthcheck`, `/api/system`) — отделяет эффект канала от эффекта прошивки.
4. **Тесты и мутации (#SA-3):** host-тесты на C (в том числе под ASAN), Node-тесты веб-слоя, проверка бандла (`node --check` каждого `<script>`). Для каждой правки — мутация, которая красит ровно один тест; образцы ответов берутся из настоящего ответа платы или печатаются настоящей функцией платы, а не выдумываются.
5. **Два независимых прохода** по диффу с разными границами проверки (код и живая плата) перед релизом; публикация — только по явному «да» владельца.
6. **Сборка воспроизводима:** повторная сборка даёт тот же sha256, что образ на плате; скан образа на утечки (MAC, SSID, почта, пути, пары «ключ=значение» с паролем) — 0, LAN-адрес только `192.168.4.1`; мощность BLE — по сгенерированному `sdkconfig`.

Не проверялось: литерал Wi-Fi-пароля в образе (хранилище секретов было закрыто при скане).

## 5. Схема приёмник → PostgreSQL

**Приёмник живёт в приватном проекте и в этот репозиторий не входит.** Схема, по которой он работает:

```
плата -- Wi-Fi, HTTP, токен --> приёмник (домашний сервер) -- транзакция --> PostgreSQL
```

- Две реализации приёмника: опрос (`af_collector`, читает `/api/history/status` и `/api/history.csv`, плата о базе ничего не знает) и приём push (`/ingest/*`, использует модули `af_collector`: `push.ingest_batch`, `PgDb`).
- **Транзакция на пачку:** `COPY` во временную таблицу → функция приёма (`af_ingest`) → курсор → журнал, одним COMMIT. Нет COMMIT — курсор не двигается; повтор пачки даёт 0 новых строк. После COMMIT число принятых строк сверяется по `count(*)` из отдельной сессии, расхождение — ошибка цикла.
- Курсор — пара `(gen, next_seq)` на прибор и кольцо; при откате счётчика на плате (`head < next_seq`) или несовпадении якорной строки фиксируется разрыв (`af_gap`, `regression`), при вытеснении старых записей — `evicted`.
- **Три базы:** до трёх баз по приоритету (основная и резервные), у каждой свой независимый курсор, поэтому резервной досылается то, что не дошло именно до неё.
- **Схема:** таблица приборов `hardware` (MAC прибора → целочисленный `hwid`), записи сырых, агрегатов и среды ссылаются на `hwid`; нарушение CHECK (например `doserate > 1000`) откатывает пачку, оператору выводится строка с причиной.
- **SSL:** между платой и приёмником шифрования нет (см. выше). Шифрование соединения приёмника с PostgreSQL в исходном проекте названо «в будущем»; его состояние в приёмнике здесь не проверялось.
- Пароли платы и базы в конфигурации приёмника не хранятся: берутся из переменных окружения или хранилища секретов.

## 6. Что не закрыто (состояние e16h на 2026-10-30; что изменилось в e16j — раздел 7)

- Настройки колец (ёмкость) зашиты константами. Период агрегации в минутах и раздельное включение колец в UI в e16h не были реализованы; в e16j есть окно агрегатов 60 с – 20 мин и раздельное включение сырых, агрегатов и среды.
- Порции 1000–100 000 строк и досылка на резервные серверы с платы не реализованы: плата отправляет пачки до 2000 строк на один приёмник.
- В e16h прямого клиента PostgreSQL на плате не было (в e16j он есть, раздел 7); по спайку: 930–1420 строк, память не блокируется; TLS в исходном проекте отложен.
- Остаточный пол ≈50 мс на маршрутах (раздел 3).

## 7. Выпуск 0.1.0-e16j (2026-11-08)

Продолжение линии e16h. Стабильный релиз `0.1.0-e16i` не выходил, был диагностический пре-релиз [v0.1.0-e16i-preview.1](https://github.com/VibeEngineering-LLC/atomfast-esp32/releases/tag/v0.1.0-e16i-preview.1) (2026-11-05); его остальные изменения входят в e16j, но TCP_NODELAY для принимаемых HTTP-соединений из пре-релиза в e16j нет (включение запланировано в следующий выпуск, без срока).

- **Отправка в PostgreSQL с платы.** Плата сама пишет сырые, агрегаты и датчики среды (запись данных среды на живой плате не проверялась); вход SCRAM-SHA-256, пароль наружу не отдаётся. Приёмник-посредник для этого пути не нужен. Раздел «Система → База данных»: состояние (вставлено, пропущено, отброшено, неудачные сессии, время входа, ошибка), настройки, «Проверить соединение», «Отправить сейчас». Позиции отправки сохраняются в памяти платы раз в 30 с и при плановой перезагрузке; «пропущено» после плановой перезагрузки на промежуточных образах b39 и b41 составило от 1 до 16, на b43 и b44 — 0 (до правки 88 730 и 50 532). Номер поколения `gen` задаётся при каждой загрузке платы (это не `boot_count`: числа на плате и в базе разные). Реальный сбой питания был на промежуточном образе до правки `gen`; после правки поведение курсора и дубли с разным `gen` при обрыве питания на плате не проверялись. Отказы сервера пережиты без перезагрузки: рестарт PostgreSQL и закрытие порта (на 2 мин на b39 и b44, на 60 с на b41), на выпускаемом образе не повторялись. Без TLS: данные и обмен идут открытыми, сеть должна быть доверенной.
- **Ключ для обновления по сети.** `/api/ota`, установка с GitHub и смена канала требуют ключа (HMAC-SHA-256 с PBKDF2, схема «вызов-ответ», одноразовое значение 120 с, привязка к методу, пути и содержимому образа). Образ проверяется потоком до переключения загрузочного раздела. После 5 неверных попыток блокировка на 60 с (потолок 3600 с), разблокировка кодом из UART. Прошивальщик 0.7.3 работает по USB и не затронут; после первой прошивки factory, после обновления с e16h и с пре-релиза v0.1.0-e16i-preview.1 ключа на плате нет.
  - *Первый ключ.* Код настройки (одноразовый) плата печатает в консоль UART0 (115200 бод) каждые 30 с, пока он активен; консоль доступна через USB-UART мост платы, для плат без моста не проверялось. Открытие COM-порта может перезагрузить плату, после чего код может смениться: берите последний напечатанный. Порядок: плата в домашней сети (в режиме точки доступа плата отказывает); на странице «Система» в карточке «Ключ OTA» ввести код в «Код настройки из UART», ключ в «Новый ключ», нажать «Задать ключ». Ключ 12–64 знака ASCII без пробелов (0x21–0x7E); у пароля полевой точки правило другое (8–63 знака, пробел допустим).
  - *Забытый ключ.* Стереть раздел NVS по USB: по таблице разделов `nvs` лежит по адресу 0x9000, размер 0x6000; команда `esptool.py --chip esp32s3 -p <порт> erase_region 0x9000 0x6000`. Стираются все настройки в NVS (настройки Wi-Fi, адреса и пароли PostgreSQL и MQTT, ключ OTA, позиции отправки в PostgreSQL, выбор прибора); приложение и раздел данных `storage` не затрагиваются. После стирания плата загрузится в режиме первой настройки (веб-интерфейс в нём может быть недоступен): домашнюю сеть записывается заново, как при первой прошивке, затем задаётся ключ по порядку выше; повторная отправка в PostgreSQL после потери позиций не проверялась. Команда из проектной спецификации, на плате в проверках e16j не выполнялась.
- **Пароль полевой точки.** Вместо общего пароля плата при первой обычной загрузке в домашней сети получает собственный случайный (12 знаков), кнопка «Показать» на странице «Система»; пока не показан, переход в режим Outdoor из интерфейса отклоняется. Заданный вручную пароль: 8–63 печатных знака ASCII; допустимый пароль пользователя сохраняется, новый генерируется, если пароля нет, он недопустим или остался прежним общим.
- **Сброс секретов.** При смене хоста или порта MQTT, PostgreSQL или HTTP-приёмника сохранённый пароль или токен сбрасывается, если не прислан новый.
- **Из e16i.** Выбор прибора (список, ручной ввод, «Забыть»); раздельное включение хранения сырых, агрегатов и среды; окно агрегатов 60 с – 20 мин; имена CSV `atomfast_<вид>_<дата>.csv`; график по агрегатам; выбор погрешности 1σ/2σ/3σ; единица мкР/ч убрана с веба; базовая и расширенная BLE-статистика (ответ `/api/ble` 749 Б без расширенной против 1142 Б с ней на одном состоянии платы); индикатор заполнения диска.
- **Ограничения e16j.** Остальной веб без пароля. p95 главной страницы 523,5 мс при RSSI около −77 дБм (было 406,6 мс при −71…−75 дБм), цель 430 мс не достигнута. Минимум внутренней RAM 55 723 Б (на e16h 80 987 Б), порог релиза 50 000 Б (решение владельца; прежний порог 60 000 Б), `alloc_fail` 0. Данные датчика среды в проверках не поступали (датчик на стенде отключён, причина по журналу не устанавливалась); запись данных среды в PostgreSQL на живой плате не проверялась. Стендовый замер образа: 71,1 мин без перезагрузок, ошибок BLE и отправки 0. На плате не проверялись: задание ключа через карточку «Ключ OTA» и заливка образа со страницы в браузере (ключ при проверках задавался скриптом), требование ключа на установке с GitHub и смене канала (на плате с ключом вызывался только `/api/ota`), блокировка перехода в Outdoor и баннер «Пароль точки изменён» (только код и тесты на хосте), поведение курсора и `gen` при реальном обрыве питания после правки `gen`, сброс секретов при смене адресата (только тесты на хосте), блокировка перебора ключа (только тесты на хосте), подмена байта в подписи образа (верный образ на плате принят), самотест HMAC, смена ключа из точки доступа, запас стека на путях OTA, холодные загрузки после генерации пароля точки, переход в точку доступа после обновления; смена прибора A→B на живой плате не проверялась.
- **Образ выпущен как есть:** это образ, прошедший замер 71 мин на плате. При повреждении хранилища ключа страница не покажет отдельного сообщения; сброс ключа возможен только стиранием NVS по USB. Исправление интерфейса войдёт в следующий выпуск.
